# 《当铺世界》v2 技术设计

## 回响织界系统（EchoWeave）

> 设计口号：话语产生回响，行动经过裁决，结果织入世界。

| 项目 | 内容 |
|---|---|
| 文档版本 | v2.0 Draft 1 |
| 编写日期 | 2026-10-11 |
| 目标游戏版本 | Probably Stolen Demo 0.46D |
| 对应工程 | AIWorldPawnshopMod |
| 核心目标 | 让开放对话安全、可靠地转化为真实世界影响 |

---

## 1. 设计摘要

“回响织界系统”是一套双路线、受监督、可恢复的世界交互架构。

第一条路线负责人物表达：理解玩家说了什么，以当前人物的身份、知识、经历和语气形成回复草稿。

第二条路线负责世界监督：独立识别玩家真正想达成的目标，检查人物回复是否误解、越权、虚假承诺或遗漏动作，并从已登记的能力中组合处理计划。

最终执行权始终属于本地规则与原版适配器。模型不能直接改写存档、调用任意游戏方法、生成并加载新代码，也不能用一句“答应了”强迫人物做不符合其利益、身份和处境的事情。

```text
玩家发言
  ↓
原版状态快照
  ├─ 人物表达路线：角色回复草稿
  └─ 世界监督路线：意图、风险、能力计划
                  ↓
            事实与人物自主裁决
                  ↓
             受控能力执行计划
                  ↓
          安全时机执行并取得回执
                  ↓
       最终回复、人物记忆、世界记录
```

## 2. 当前问题

现有版本已经可以处理议价、寻物、回访、临时库存、交换、关系和摘要记忆，但主要通过固定提案字段与独立解析器连接。开放交谈继续扩展后，会出现以下问题：

1. 新意图没有对应字段时，人物可能只在文字上答应，世界没有真实变化。
2. 人物是否理解请求、是否有能力、是否愿意帮助，容易被混成同一个判断。
3. 模型返回期间，顾客、商品、交易阶段或来客队列可能已经变化。
4. 多步骤要求缺少统一的顺序、去重、延期、补偿和恢复机制。
5. 接口超时或输出异常时，缺少按风险分级的降级路径。
6. 新玩法不断添加专用字段，会使请求格式和运行入口持续膨胀。
7. 人物承诺、实际执行和最终结果之间没有统一的追踪链路。

v2 的目标不是让模型拥有无限权限，而是让它使用一组稳定的世界动作，组合出更多开发时没有逐句预设的合理流程。

## 3. 目标与非目标

### 3.1 目标

- 理解未预先列举、但可由现有动作组合完成的要求。
- 统一判断人物身份、知识、利益、风险、关系和当前处境。
- 区分“愿意尝试”“明确接受”“保证完成”和“真实办成”。
- 所有世界影响都经过本地事实校验与能力白名单。
- 对重复响应、状态变化、突然退出和部分失败具备恢复能力。
- 保持原版剧情、来客规则、交易流程和强制事件的最高优先级。
- 模型不可用时继续游戏，并保留本地内容与确定性功能。
- 渐进包装现有组件，避免一次性重写整个 Mod。

### 3.2 非目标

- 不允许运行时生成、编译或加载新的 C# 补丁。
- 不开放任意反射、任意字段写入或任意方法调用。
- 不保证玩家提出的每个要求都能实现。
- 不让扩展关系覆盖原版人物的身份和剧情事实。
- 不因好感高就突破阵营、渠道、风险或剧情限制。
- 不用监督模型替代本地规则。

## 4. 核心术语

| 名称 | 定义 |
|---|---|
| 回响 | 玩家发言形成的候选意图、承诺或世界动作 |
| 织界 | 已验证动作在安全时机真正作用于游戏状态 |
| 人物表达器 | 负责身份一致、自然语言和情绪表现的模型路线 |
| 世界监督器 | 负责意图发现、计划审查、遗漏检查和回复纠正的路线 |
| 事实裁决器 | 根据原版状态和确定性规则判断计划是否成立 |
| 人物自主门 | 判断人物能否帮助、是否愿意以及愿意承诺多少 |
| 能力图谱 | Mod 允许模型引用的受控动作目录 |
| 意图账簿 | 只追加记录请求、批准、执行、延期、失败与结果的日志 |
| 安全时机 | 某类动作允许执行的游戏阶段 |
| 执行回执 | 能力执行后的真实结果，人物最终表述的事实依据 |
| 能力缺口 | 请求合理，但目前没有受控动作可以兑现 |

### 5.1 自适应调用

| 风险级别 | 场景 | 处理方式 |
|---|---|---|
| 快速级 | 普通闲聊 | 只生成人物回复，不允许世界副作用 |
| 标准级 | 单步骤低风险请求 | 两条路线并行，本地规则合并 |
| 重要级 | 交易、物品、关系承诺、跨天效果 | 双路线审查，执行后按回执修正回复 |
| 严格级 | 多人物、阵营冲突、稀有物品、敏感效果 | 增加短复核，不确定时追问或拒绝 |

双路线不应每轮固定串行。普通闲聊避免第二次请求；高风险动作才执行完整审查，以控制等待时间和接口费用。

## 6. 单回合流程

### 6.1 状态快照

快照至少包含：

- 世界标识、当前日、会话标识、回合号和状态修订号。
- 当前顾客、电话联系人、原版人物标识和显示名称。
- 原版剧情事实、身份背景、专属台词和知识边界。
- 当前来意、买卖方向、预算、耐心、库存和柜台商品。
- 个人关系、阵营声望、近期记忆和未完成承诺。
- 世界事件、未来来客候选和原版队列限制。
- 当前场景允许使用的能力摘要。

模型不能接收 Unity 对象、内存地址或运行实例，只能使用稳定键和序列化快照。

### 6.2 人物表达路线

输出人物回复草稿、情绪、主观理解、帮助倾向、理由以及需要追问的内容。该路线不拥有执行权限，即使文字说“我答应”，也只能视为候选承诺。

### 6.3 世界监督路线

- 独立识别玩家目标，避免完全依赖人物草稿。
- 检查角色是否误认人物、商品、金额、时间或场景。
- 发现可由多个能力组合完成的新流程。
- 标记过度承诺、无依据事实、遗漏条件和风险。
- 指出请求所需能力及执行顺序。
- 能力不足时生成缺口记录与自然回应约束。

### 6.4 本地裁决顺序

1. 请求对象是否仍为当前人物。
2. 对话返回时场景是否仍有效。
3. 人物和物品是否能唯一解析。
4. 原版事实是否支持模型判断。
5. 当前人物客观上能否完成或转交请求。
6. 当前人物主观上是否愿意帮助。
7. 涉及第三方时，目标人物是否也愿意。
8. 能力是否登记，参数和风险是否合规。
9. 同类动作是否已执行或正在等待。
10. 执行是否会覆盖剧情人物或原版强制状态。

### 6.5 执行与表述

即时动作在当前安全时机执行；延期动作进入账簿，由换日、人物生成或界面就绪事件唤醒。人物最终回复只能陈述回执允许的事实，关系与记忆也应在真实结果确定后写入。

## 7. 人物自主门（Agency Gate）

人物自主门专门回答四个不同问题：

1. **能不能做**：是否有渠道、知识、物品、时间和原版条件。
2. **愿不愿做**：是否符合人物利益、关系、阵营、性格和当前情境。
3. **愿意承诺多少**：保证完成、愿意尝试、要求条件，还是只肯转告。
4. **最后有没有办成**：受后续世界状态、目标人物态度和随机结果影响。

这四层必须分开。人物答应尝试，不等于事情一定成功。

### 7.1 人物自主档案

```csharp
public sealed class AgencyProfile
{
    public string CharacterKey { get; init; } = string.Empty;
    public int Helpfulness { get; init; }
    public int SelfInterest { get; init; }
    public int RiskTolerance { get; init; }
    public int Reliability { get; init; }
    public int FactionLoyalty { get; init; }
    public int Lawfulness { get; init; }
    public int Discretion { get; init; }
    public int Sociability { get; init; }
    public List<string> HardBoundaries { get; init; } = new();
    public List<string> Motivations { get; init; } = new();
}
```

命名人物使用稳定档案；普通顾客根据原版标签、职业、阵营和角色原型建立临时档案。来源优先级如下：

1. 原版剧情变量和明确身份事实。
2. 原版专属台词体现的行为倾向。
3. 阵营和职业规则。
4. 玩家与人物的历史记忆。
5. 普通顾客原型默认值。

模型可以帮助总结倾向，但不可覆盖硬边界。

### 7.2 请托评估上下文

```csharp
public sealed class AssistanceRequest
{
    public string RequestKind { get; init; } = string.Empty;
    public string ActorKey { get; init; } = string.Empty;
    public string TargetKey { get; init; } = string.Empty;
    public int Cost { get; init; }
    public int Risk { get; init; }
    public int TimeBurden { get; init; }
    public int FactionConflict { get; init; }
    public int StoryConflict { get; init; }
    public int OfferedBenefit { get; init; }
    public int Urgency { get; init; }
    public bool RequiresSecrecy { get; init; }
    public bool RequiresThirdPartyConsent { get; init; }
}
```

还应考虑个人关系、阵营声望、玩家是否兑现过承诺、过去的帮助或欺骗、请求是否符合职业、是否欠人情、报酬是否合理、是否危害本人或同伴，以及人物是否处于原版剧情任务中。

### 7.3 硬性阻断

下列情况不进入普通评分，直接限制：

- 人物不认识目标且没有联系方式。
- 原版剧情明确禁止人物当前行动。
- 请求要求人物背叛不可动摇的身份约束。
- 请求对象、商品或期限无法唯一确定。
- 当前能力无法表达该动作。
- 行为会破坏原版关键流程或覆盖强制来客。
- 请求建立在人物不可能知道的事实之上。

硬性阻断可以产生澄清、建议玩家改用电话、寻找中间人、等待条件变化或明确拒绝。

### 7.4 意愿评分

通过硬性检查后，本地规则计算标准化意愿值。模型只提供解释和语境分类，最终数值由本地代码生成。

```text
意愿 = 人物助人倾向
     + 个人关系影响
     + 阵营态度影响
     + 请求与身份一致度
     + 报酬与互惠收益
     + 玩家可信度
     + 欠情或共同利益
     - 实际成本
     - 人身或经济风险
     - 阵营冲突
     - 剧情冲突
     - 时间负担
     - 反复施压惩罚
```

各项映射到 `-100..100`：

| 分数 | 倾向 | 允许的承诺 |
|---:|---|---|
| 45 至 100 | 愿意 | 明确接受，但仍区分尝试和保证 |
| 20 至 44 | 有条件接受 | 要求报酬、时间、物品或降低范围 |
| -19 至 19 | 犹豫 | 追问、讨价还价或暂不表态 |
| -44 至 -20 | 不愿意 | 符合身份地拒绝，可给替代建议 |
| -100 至 -45 | 强烈拒绝 | 可能产生冒犯、戒备或关系变化 |

决策使用世界标识、人物键、请求键和当前日形成稳定随机种子。同一状态下重新加载，不应得到完全相反的答复。

### 7.5 承诺等级

```text
guaranteed        能力确定、人物可靠且结果主要由本人控制
accepted          接受执行，但可能受外部条件影响
will_try          愿意尝试，不保证结果
conditional       满足报酬、时间或其他条件后才接受
negotiating       正在讨论条件
clarification     需要补充目标、范围或期限
refused           明确拒绝
unable            愿意但客观无法完成
deferred          当前不能决定，等待安全时机或新事实
```

模型不得把 `will_try` 写成“我保证办到”。最终回复生成器应根据裁决和执行回执纠正措辞。

### 7.6 第三方请求的两段式同意

涉及第三方时，至少有两次独立自主判断：

1. 当前人物是否愿意替玩家传话或采取行动。
2. 目标人物收到消息后，是否愿意接受请求。

第一人答应传话，不能直接等价为目标人物答应来访、寻找物品或进行交易。

### 7.7 联系路径

```text
direct_phone          直接电话
same_faction          同阵营渠道
story_relationship    原版剧情明确认识
business_network      职业或交易网络
player_introduction   玩家曾建立联系
indirect_contact      需要中间人，可靠性较低
none                  无法联系
```

传达结果可以是已送达、延迟、找不到目标、目标拒绝接收、消息失真或等待回应。可靠性受传话人的信誉、保密性、风险和世界事件影响。

## 8. 能力图谱（Capability Atlas）

### 8.1 能力契约

```csharp
public interface IWorldCapability
{
    CapabilityDescriptor Descriptor { get; }
    CapabilityCheck Check(CapabilityInvocation invocation, WorldSnapshot snapshot);
    CapabilityReceipt Execute(CapabilityInvocation invocation, WorldExecutionContext context);
    ReconciliationResult Reconcile(IntentProjection intent, WorldSnapshot snapshot);
    CompensationResult Compensate(CapabilityReceipt receipt, WorldExecutionContext context);
}
```

每项能力必须声明稳定键、版本、用途、参数结构、允许场景、安全时机、前置条件、风险、影响、去重字段、对账方式、补偿方式以及失败时允许人物怎样表述。

### 8.2 风险等级

| 等级 | 示例 | 要求 |
|---|---|---|
| R0 只读 | 查询人物、物品和关系 | 本地检查即可 |
| R1 扩展状态 | 摘要记忆、待办、关系候选 | 可撤销、必须去重 |
| R2 原版可恢复 | 来客候选、报价约定 | 双路线审查、执行后对账 |
| R3 原版敏感 | 物品生成、跨人物任务 | 严格模式、延期执行、完整回执 |
| R4 禁止开放 | 任意写字段、跳过剧情、删除原版对象 | 不注册 |

### 8.3 首批能力

```text
character.resolve
character.check_contact
message.relay
social.task.create
visit.request.self
visit.request.third_party
procurement.request.goods
inventory.reveal.carried
trade.adjust.selected
trade.adjust.all
barter.open.native
wallet.transfer.native
memory.append.summary
relationship.propose.change
world.propose.event
dialogue.ask.clarification
```

监督器可以重新组合这些动作。如果缺少必要能力，系统写入 `CapabilityMissing`，阻止人物虚假宣称成功，并给出符合身份的拒绝或替代建议。

## 9. 执行计划

```csharp
public sealed class WorldActionPlan
{
    public string PlanKey { get; init; } = string.Empty;
    public string IntentSummary { get; init; } = string.Empty;
    public string SnapshotRevision { get; init; } = string.Empty;
    public List<WorldActionStep> Steps { get; init; } = new();
    public string ExecutionPolicy { get; init; } = "ordered";
}
```

限制：

- 最多八个步骤。
- 禁止递归、任意循环和模型自定义方法名。
- 参数只能来自快照、玩家明确内容或先前步骤回执。
- 修改后的计划必须重新验证。
- 每回合最多一个主要原版副作用，其余可延期。
- 计划不能持有原版运行对象。

执行策略：

```text
all_or_nothing    整笔交换等不可拆分动作
ordered           转达、邀请、寻物等有先后关系的流程
best_effort       摘要记忆和有限反馈
deferred          等待换日、人物生成或界面就绪
native_confirmed  必须由原版界面完成最后确认
```

## 10. 意图账簿（Intent Ledger）

### 10.1 状态机

```text
Proposed
 ├─→ ClarificationRequired ─→ Proposed
 ├─→ Rejected
 ├─→ CapabilityPending
 └─→ Approved
       └─→ Scheduled
             └─→ Ready
                   └─→ Executing
                         ├─→ Fulfilled
                         ├─→ RetryableFailure ─→ Scheduled
                         ├─→ Conflict ─→ ClarificationRequired / Superseded
                         ├─→ PermanentFailure
                         └─→ Compensating ─→ Compensated
```

跨天请求允许进入 `Expired`。到期后人物应说明没有办成，不能让承诺无声消失。

## 11. 完整示例：邀请第三方并请求带货

玩家输入：

> “你去找红魔鬼代表，让他明天过来，再帮我带两瓶水，我出高价。”

系统拆解：

```text
1. resolve_character("红魔鬼代表")
2. check_contact(当前顾客, 红魔鬼代表)
3. evaluate_assistance(当前顾客, 转达请求)
4. relay_message(当前顾客, 红魔鬼代表)
5. evaluate_assistance(红魔鬼代表, 来访与寻物请求)
6. request_third_party_visit(红魔鬼代表, 明日)
7. request_goods(红魔鬼代表, 水, 数量 2, 高价条件)
```

可能结果：

- 当前顾客不认识目标：建议玩家直接打电话，不创建任何后续记录。
- 当前顾客认识但不愿帮助：按人物身份拒绝，可能影响关系。
- 当前顾客愿意传话：只记录传达任务，不保证目标接受。
- 目标愿意来但不愿找货：只建立来访候选。
- 目标愿意找货：成功率仍受渠道、稀有度、供给、关系和价格影响。
- 原版队列已满：不挤掉剧情顾客，在允许期限内顺延。

任一阶段都不得提前宣称后续阶段已经成功。

## 12. 冲突、退出与恢复

### 12.1 状态变化

模型返回时顾客已经离开：不得把动作应用到新顾客。即时议价失效；已批准的跨天请求可进入账簿等待后续时机。

### 12.2 承诺修改

先说五折、后改八折时，使用人物、交易和商品集合组成冲突键。后一条明确表达替代旧约定；新表达含糊则必须追问。

### 12.3 去重

```text
世界标识 + 会话标识 + 回合号 + 能力键 + 标准化参数
```

同一响应再次到达时返回原回执，不重复加关系、生成物品或安排来访。

### 12.4 三阶段执行

1. 写入 `ExecutionStarted`。
2. 调用原版适配器。
3. 写入 `EffectCommitted`。

重新启动后发现未闭合动作时执行对账：原版效果存在则补写恢复事件；未发生则重新排队；无法判断则标记冲突，禁止盲目重试。

## 13. 故障降级

| 故障 | 处理方式 |
|---|---|
| 人物表达器不可用 | 使用本地人物回复，保留确定性解析 |
| 世界监督器超时 | 安全文字可显示，未验证动作全部移除 |
| 两条路线冲突 | 原版事实和本地规则优先，必要时追问 |
| 返回格式错误 | 最多一次结构修复，仍失败则降级 |
| 状态修订号变化 | 取消旧动作，以新快照重新判断 |
| 能力不存在 | 写入能力缺口，不虚构办成 |
| 执行失败 | 根据回执重试、延期、补偿或说明失败 |
| 扩展存档损坏 | 从最后有效事件和最近快照恢复 |
| 网络完全不可用 | 继续本地内容和原版玩法 |

本地规则优先级始终高于两个模型。

## 18. 验收标准

### 人物自主

- 同一请求因人物身份、关系、阵营和风险得到不同回应。
- 高好感不能绕过硬性渠道或剧情限制。
- 人物可以附条件接受、只愿尝试或直接拒绝。
- 传话人答应不等于目标人物接受。

### 世界真实性

- 人物没有完成动作时，不得声称已经完成。
- 每个重要承诺都能在账簿中找到状态和结果。
- 跨天请求不会静默消失。
- 原版强制来客和剧情状态优先。

### 健壮性

- 重复处理同一回复不会重复产生副作用。
- 回复返回时换了顾客，不会污染新人物。
- 执行期间退出，重新进入后可以对账恢复。
- 任一模型不可用时，游戏仍可继续。
- 扩展存档异常不阻止原版加载。

## 19. 测试计划

### 单元测试

- 人物自主评分边界和硬性阻断优先级。
- 承诺等级映射和稳定随机。
- 联系路径、能力参数、去重键和冲突键。
- 意图状态迁移。

### 集成测试

- 店内顾客和电话联系人同时存在。
- 买家临时库存与原版购买任务并存。
- 转达、目标答复、候选来访和最终到店全链路。
- 限定商品议价后新增商品。
- 交换窗口打开、取消和完成。
- 原版来客队列满时的延期行为。

### 故障注入

- 人物表达请求超时。
- 世界监督返回非法结构。
- 两条路线意见相反。
- 原版对象在执行前消失。
- 写入开始后立即退出。
- 同一网络响应重复到达。
- 扩展账簿尾部损坏。

## 20. 已确定的架构决策

1. 正式名称为“回响织界系统（EchoWeave）”。
2. 人物表达和世界监督是职责不同的两条路线。
3. 监督模型只能规划和审查，不能直接修改游戏。
4. 模型可以组合已登记能力，但不能在运行时创造代码。
5. 人物是否愿意帮助由人物自主门裁决，不由模型的接受字段直接决定。
6. 涉及第三方时，传话人与目标人物分别作出决定。
7. 接受尝试、承诺完成和真实成功必须分别记录。
8. 所有重要动作通过意图账簿、去重键和执行回执追踪。
9. 原版事实、剧情和队列拥有最终优先级。
10. 默认采用自适应审查，避免每句闲聊都增加完整请求。
