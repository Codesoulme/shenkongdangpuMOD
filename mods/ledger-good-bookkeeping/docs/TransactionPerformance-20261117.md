# 交易卡顿调查（2026-11-17）

## 结论与范围

已复现 1.1.8 账本记录路径上的明显同步耗时。`Record -> Save -> Flush` 在交易调用线程上序列化整份 `CreditLedgerData`，再执行 `File.WriteAllText` 和带备份的 `File.Replace`。其中包括本次交易没有修改的全部 `SaveSnapshots`。

初次调查时只增加诊断基准与调查记录，未改动运行时或发布。随后用户授权修复并直接推送，1.1.9 实现与验证见文末。

## 复现方式

测试工程直接编译生产记录、交易补丁、存储及明细代码，使用游戏对象替身在临时目录执行真实 JSON 序列化和磁盘写入。真实账本文件仅读取为模板，所有写入都在独立 `LedgerRegression-*` 临时目录。

```powershell
dotnet run --project mods/ledger-good-bookkeeping/tools/LedgerRegression/LedgerRegression.csproj -c Release -- --benchmark --performance --fixture '<CreditLedger.json 的完整路径>'
```

不传 `--fixture` 时使用合成数据。每项计时预热后采样 9 次，报告中位数、最大值及当前线程内存分配量。完整测试输出同时测量相同数据的纯序列化、预先序列化字符串的原子写盘，以区分 CPU 与 I/O。序列化和写盘计时分别执行，不能将各自中位数当成精确的同一次调用拆分。

| --- | ---: | ---: | ---: | ---: | ---: |
| 本机账本副本：126 条当前记录，33 份快照内合计 3173 条 | 1.45 MB | 56.93 | 60.27 | 29.40 | 31.51 |
| 126 条当前记录，无历史快照 | 0.053 MB | 24.83 | 30.20 | 0.64 | 26.36 |

第一轮本机账本副本单笔 65.42 ms、100 件批量 49.43 ms，重复测量均呈现明显保存阻塞。较大合成文件代表增长压力，不能当作反馈玩家的实际文件规模。

本机账本副本单笔交易约分配 5.66 MB；合成 14.70 MB 文件单笔约分配 56.68 MB。较多临时分配也会增加垃圾回收压力，但本次没有在 Unity 内量化垃圾回收停顿。

简单瓶装水明细采集 100 次合计 0.11 ms，信用点未知来源栈检查 100 次合计 1.07 ms。该对照不能排除装有大量子物品、复杂事件的容器在真实游戏中的额外开销。

## 已核对的其他路径

- 当前游戏的 `NegociationUIManager.SellMultiple`、`BuyMultipleItem`、`OnWholesaleClick` 已分别有持久化批处理补丁。100 件批量操作只在订单结束保存一次，但这次全量保存仍阻塞。
- 当前游戏 `PlayerStore.BuyAllItemFromTable` / `SellAllItemFromTable` 原生方法直接修改信用点，没有逐件调用 `BuyItem` / `SellItem`。不能仅因为没有上述批处理补丁，就判定这里存在逐件重复写盘。
- 同符号的批量收支已有合并飘字逻辑。一次批量交易创建几百个飘字不是本次存储基准测到的问题。Unity 实际 Canvas/TMP 构建成本不包含在基准中，仍需游戏内分析才能定量。
- 原生账本页在切页时渲染，没有发现它在每笔交易时重新构建整张表。
- 本机日志显示同 ID 的工坊副本被本地版本覆盖跳过，未发现该副本重复运行或账本异常刷屏的证据。
- 当前记录列表限制为 1000 条，但旧存档及轮转存档的快照字典没有相应清理上限。日常交易保存成本会随历史存档增长，而非只随当天交易数量增长。

## 初次调查建议

1. 将日常交易写入与存档快照归档分开。交易只持久化新增记录或小型当前账本，不在每笔交易时序列化/重写不变的历史快照。
2. 保存、读取存档、停用模组时设置明确的持久化边界，并保留原来的读档回滚语义。若采用追加日志，必须覆盖尾部写入中断、重复回放、快照提交后崩溃以及旧格式迁移。
3. 依据真实仍存在的存档轮转文件设计快照清理，不能直接删除旧快照来换取速度，否则旧档可能无法恢复正确账本。
4. 不建议只把同步保存延后一帧：这会将同样的卡顿搬到另一帧。异步写入也需处理线程安全、退出刷盘和写入顺序，不能直接对可变 `_data` 使用后台任务。
5. 完成存储优化后再测真实游戏的复杂容器、飘字 Canvas 查询/TMP 创建和整体帧耗时。本次证据足以确定保存路径是一个显著瓶颈，但不能断言它解释所有玩家环境中的卡顿。

基准输出里的分配量并非常驻内存；文件写入延迟受本机磁盘、文件系统及安全软件影响，不能作为其他玩家机器的绝对预测值。

## 1.1.9 实现与验证

- 日常 `Flush` 只序列化 `_pending`，追加一条以换行结束的 JSON 批次到 `CreditLedger.transactions.jsonl`。批量订单一批追加一次；失败追加保留内存中待写记录，下次重试先截回上次已提交长度，不重复追加半笔记录。
- `CreditLedger.json` 保留兼容的完整账本及历史快照。存档、存档轮转、读档、停用时原子归档，不再在日常交易中写它。旧文件首次加载自动生成代次标识，旧世界文件迁移在构造完成后才归档，修正旧代码在 `_data` 赋值前调用保存的问题。
- 归档先提交新 `JournalGeneration`，再清理日志。若在两步之间退出，旧日志因代次不同而跳过；读档亦切换代次，阻止废弃时间线回放。恢复只读取完整批次，丢弃未写完的尾部。日志重放与内存都保留最近 1000 条当前流水，历史存档快照继续保留。
- 手动备份需要包含完整数据目录。回退旧版前须正常停用新版／正常退出，旧版无法读取未归档的增量日志。

相同基准、同一数据模板，9 次采样中位数：

| 数据集 | 单笔原耗时 → 1.1.9 | 100 件批量原耗时 → 1.1.9 |
| --- | ---: | ---: |
| 现有 1.45 MB 文件 | 56.93 → 0.42 ms | 60.27 → 2.40 ms |
| 无历史快照 | 24.83 → 0.47 ms | 30.20 → 1.48 ms |
| 33 × 1000 条快照，14.7 MB | 311.58 → 0.36 ms | 305.03 → 1.44 ms |
| 100 × 1000 条快照，44.4 MB | 1039.76 → 0.62 ms | 1005.53 → 1.85 ms |

现有数据单笔分配从约 5.66 MB 降到 9.4 KB，100 件批量从约 6.58 MB 降到 304 KB。真实 Unity 帧耗时仍未测量；完整归档在存读档时仍有同步成本，不能将此数据描述为游戏整体帧率提升。

56 项账本、29 项飘字检查通过，新增覆盖：交易不改写快照归档、批量一行增量、旧日志在归档中断后不重放、增量尾部截断恢复、最新／历史存档时间线切换、旧格式与字段迁移、1000 条上限、追加失败重试、归档失败后的继续记录、读档归档失败后丢弃旧时间线待写批次及旧世界文件迁移。Release 零警告、零错误。

本机官方扫描器 v4 检测到的能力仍只有 `files`，无 HardFlags、无扫描错误。既有 `SaveFiles.RotateIntoHistory` 补丁出现在 Pending 的 files 规则中，清单已声明；未增加网络、外部反射、动态代码、原生库或进程权限。扫描报告保留该原始发现，检查工具只允许声明过的 files 待生效规则。
